# ADR 0005 — Dimensions and hatches are generated, not stored

**Status:** Accepted
**Date:** 2026-08-11

## Context

DWG stores a dimension as a DIMENSION entity carrying a handful of definition
points *plus* a reference to an anonymous block containing the lines, arrowheads
and text other CAD software generated from them. It stores a hatch as a boundary plus a
pattern definition, and regenerates the fill on demand.

For dimensions that leaves a choice: display the file's block, or regenerate
from the definition points.

## Decision

**Both are generated from their definition on demand. Neither stores its drawn
result.**

For a dimension, `DimensionEntity::generate(const DimStyle&)` produces the
lines, arcs, arrowheads and text each time they are needed. The anonymous block
the file supplied is kept in `blockHandle` but never drawn.

For a hatch, `HatchEntity::generateLines(clip)` produces the pattern segments
each time, clipped to the region asked for.

### Why, for dimensions

Displaying the block would be less work and would match the file byte for byte
on load. It would also make a dimension a picture rather than a dimension:

- Dragging an extension line origin would move the definition point and leave
  the drawn geometry where it was.
- Changing a dimension style would restyle nothing until every dimension was
  regenerated by something.
- A dimension read from a file with no block — which is legal, and which this
  application's own writer produces — would display as nothing.

The last one is decisive. Regeneration is the path that always works, so it is
the only path.

The cost is that a dimension may not look pixel-identical to the way other CAD software
drew it. That is the right trade: an editable dimension that differs slightly in
arrowhead shape is a dimension; a faithful one that cannot be edited is a
drawing of a dimension.

The block reference is preserved rather than dropped so that a file saved from
here still carries what another application expects to find.

### Why, for hatches

Storage is the argument. A hatched wall section covering a site plan is tens of
thousands of segments at one zoom level and a hundred at another; storing the
generated lines would store the worst case permanently, and would still be wrong
after any edit to the boundary.

Because generation is view-dependent, `generateLines` takes the clip bounds.
A hatch covering a whole drawing costs the same as one covering a doorway when
both are zoomed to the same window — the single mechanism that makes hatch-heavy
drawings usable.

It also takes a hard segment cap. Hatch generation is the one part of scene
building whose cost is not bounded by entity count: a pattern scale of 0.001 in
a corrupt or badly imported file would otherwise generate segments until memory
ran out. The clip keeps the work proportional to the view; the cap keeps it
proportional to *something* when the pattern scale is nonsense.

## Consequences and known limits

- Dimension styles work the way styles are supposed to: change one, and every
  dimension using it redraws.
- Dimensions and hatches are editable by their definition points, through the
  ordinary grip mechanism.
- Both are `toCurves`-backed, so snapping, picking and trimming treat them like
  any other entity. A hatch deliberately exposes only its *boundary* — snapping
  to a hatch line would be maddening, and there can be a hundred thousand.
- **Not implemented, deliberately:**
  - *Seed-point boundary tracing.* `HATCH` takes its boundary from a selection.
    Picking an empty spot and having the region worked out needs a planar
    arrangement of every nearby edge, which is a substantially larger algorithm.
    Selecting the boundary is the honest subset, and it is what the
    associativity data records anyway.
  - *NURBS spline boundary edges.* Preserved verbatim so they round-trip, and
    drawn as a polyline through their fit points. The kernel has no NURBS curve
    yet; approximating the display while keeping the data exact loses nothing on
    save.
  - *Gradient fills.* Preserved and drawn flat in the first colour. A visibly
    approximate fill is recoverable; a lost one is not.
  - *Tolerances and alternate units on dimension styles.* Carried through
    unmodified as preserved group codes, so a drawing that uses them is not
    damaged by being opened here.

## One convention that had to be chosen

DXF group 73 on a hatch arc edge is documented only as "is counterclockwise
flag", and two readings are in circulation: that it reverses the *traversal* of
the loop, or that it means the angles were *measured* clockwise and the arc is
therefore mirrored.

This implementation takes the first. The flag exists so a closed boundary can
run end to end when an edge is shared with a neighbour that traverses it the
other way; only the direction is needed for that, and the mirror reading makes
one flag change both the geometry and the direction. The choice is pinned by a
test so it cannot drift silently.
